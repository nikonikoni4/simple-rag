## 问题界定

### 问题简述

跨文件合并 chunk（见 [切分与合并分离](2026-10-01-切分与合并分离.md)）让 `file_path` 从单值变成多值。由此必须重新决定：**正文、path、元数据分别存在哪张表，检索时按 `chunk_id` 从哪张表取**。

此前 [检索层以 vec 为中心](2026-09-29-检索层以vec为中心.md) 的立场建立在「正文存在 vec0」「没有第二个存正文的地方」之上。`file_path` 多值化让这个前提不再成立：vec0 的 KNN 里 metadata 列只认 `=`（实测），多值列表既不能过滤也难维护。

### 讨论范围

- 向量表 / 数据表两者的字段划分
- 检索返回 path 与正文的取数路径
- 按文件定位 / 删除 / 过滤**各自在单表内**的实现路径
- 对既有 ADR《检索层以 vec 为中心》的影响（修订而非推翻）

### 非讨论范围

- 合并算法与切分策略（见 [切分与合并分离](2026-10-01-切分与合并分离.md)）
- 文件名前缀是否可配置（另行决策）
- 检索层的 RRF 融合策略（不变）
- `chunk_id` 的口径（用户自行决定）
- **扩展字段的具体设计** —— 模块定基本字段，其余列由调用方声明（与 vec0 现有的 `Schema.fields` 机制一致）。加什么列、列名怎么起、要不要可过滤，是调用方的决定，本 ADR 不讨论
- **跨两张表的联合操作** —— 同事务写两张表、按 `path` 的完整删除、按 `path` 过滤的 KNN。三者都要求两张表协同，留到后续「收口」，见「后续影响」

### 模糊信息的明确定义

- `基本字段`：模块自己工作要用的那一批字段，DDL 由模块固定生成，写入时必须给
- `分表`：把正文与 path 从 vec0 移到普通 SQLite 表
- `每次查询都需要返回 path`：检索结果要能定位回原文档（用户判断：chunk 切分后上下文有丢失，通过查看具体文档可能更好）

### 问题深度

架构层：存储分层与「数据中心放哪」的位置决策，决定 schema 的演进成本与后续所有存储层改动。

## 现状

- 当前 vec0 表存正文（`Schema.fields` 里的字段都在 vec0 上，包括 `content`）
- 上一版 ADR《检索层以 vec 为中心》的前提是「正文存在 vec0」「没有第二个存正文的地方」——**该前提即将失效**
- vec0 不能 `ALTER` 列，加字段要重建表；而模块**读不回旧向量** → 重建 = 全量重嵌
- 实测（`explore/sqlite-vec/probe_24`）：vec0 的 KNN 里 metadata 列只认 `=`，`like` 直接报 `An illegal WHERE constraint was provided on a vec0 metadata column`；`=` 匹配整个值，对 JSON list 只命中单文件块
- 实测（`explore/sqlite-vec/probe_25`）：`chunk_id in (子查询)` 形态可用 —— 候选集 500 时 3.3 ms、5000 时 29 ms（随候选集线性）；无过滤 0.124 ms；且 vec0 是**先过滤再 KNN**，不会静默少返回
- 实测（`explore/sqlite-vec/probe_24` §5）：完整「按文件删」链路（定位 + 删 vec0 + 清数据表行）5.1 ms

## 决策前提

- **前提 1：当前数据量在千级** —— data/lifeprismData 有 382 个 `.md`（diary 371 个），按已测的「30 文件 / 263 chunk」外推，约 3000~5000 chunk；探针 25 在 5000 行规模验证过。实测在这个量级下，分表与单表的查询效率**没有明显区别**
- **前提 2（用户判断）：每次查询都需要返回 path** —— chunk 切分后上下文有丢失，通过查看具体文档可能更好。因此「检索结果带回 path」不是可选功能
- **前提 3：跨文件合并会发生**（见 [切分与合并分离](2026-10-01-切分与合并分离.md)），因此 `file_path` 更多值
- **前提 4：`file_path` 多值后，vec0 上无法再做「按文件」的过滤**（实测：LIKE 报错、`=` 漏合并块）
- **前提 5：两张表用的是同一套字段模型** —— 模块定基本字段，其余列由调用方声明（用户原话：「当前数据表和向量表都有基本字段（写入时必须写入），其他字段设计由外面给出列，这个和当前 vec0 的扩展方式是一样的，只不过 vec0 他要区分 metadata 和辅助列」）

## 可选方案

### 方案 1：分表（vec0 保持原样 + 新增数据表）

**vec0 不做任何改动**：模块自己用的仍是 `chunk_id` / `created_at` / `updated_at` / `embedding` 四个基本字段，其余列照旧由调用方通过 `Schema.fields` / `filterable` 声明。DDL 生成、`insert` / `search` / `get` / `update` / `delete` 全部保持原样。

**新增数据表**，基本字段七列：`chunk_id` / `path` / `start_line` / `end_line` / `created_at` / `updated_at` / `content`。一个 chunk 有多个 path 时**分行存放**，`chunk_id` 与 `path` 各建索引。数据表同样允许调用方声明扩展列。

`path` 进数据表，是因为 ADR 的两条前提都要它：每次查询必须返回 path（前提 2），更新文档时也要靠 path 定位（见下方 `delete_by_path`）。

`start_line` / `end_line` 跟着 `path` 一起分行。**这一对列是刻意偏离「如无必要勿增实体」的一处** —— 它的动机是**简单**，不是必要性：分行存储后，每一行的 `path` 天然对应自己那段的区间，模块顺手写进去即可；若交给调用方在外面另建表维护，反而要重做一次 path 与行区间的对应关系。用户原话：「这里是为了简单才做的，不是因为他是必须的」。

**优势**

- **数据与 vec0 解耦**：正文放进普通表后，加字段走普通表 `ALTER`，**不需要重嵌**
- **能做更灵活的 SQL 组合**：过滤条件用普通表任意 SQL 表达（按文件 / 文件夹 / 日期 / 组合），拿 chunk_id 再喂 KNN —— `path` 的过滤是 vec0 做不到的（前提 4）
- 数据表绕开 vec0 的全部限制：不能 ALTER、16 列上限、删除不回收空间

**劣势**

- 两张表需同事务维护（探针 12 已证普通表与 vec0 可同事务）
- 检索需回查一次取正文 + path
- path 多值时，同一 chunk 在数据表里占多行，`content` 与时间戳这几列逐行重复 —— 换取的是按文件定位能走索引

### 方案 2：vec0 存正文 + 数据表只存 path 映射

**优势**

- KNN 一次取回正文（若不需要 path）

**劣势**

- 正文仍绑在 vec0 上（加字段 = 重建 + 全量重嵌）
- 前提 2 下仍要回查 path → 查询次数与方案 1 相同，却多背负 vec0 的列数限制

### 方案 3：单表，全部塞进 vec0

`file_path` 存 JSON 数组文本，全部数据留在 vec0。

**优势**

- 一次查询取回全部；无第二张表；实现最简单

**劣势**

- 按文件的 KNN 过滤做不到（LIKE 报错、`=` 漏合并块）—— 要做只能用 `in (子查询)`，而子查询的数据源必然在另一张普通表，等于绕回分表
- 加字段 = 重建 vec0 + 全量重嵌
- 按文件删除退化为 LIKE 全表扫（探针 24：30 ms vs 数据表索引 5 ms，6 倍）

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1（千级，效率无显著差异）+ 前提 2（必返回 path）成立 | 方案 1 | 当前选择 |
| 前提 2 失效（出现不需要 path 的主场景，只需正文） | 方案 2 / 3 的「一次查询」优势才成立 | 备选触发（见下） |
| 前提 1 失效（数据量涨到分表开销显著） | 重新审议 | 备选触发（见下） |

**用户明确表示不预设切换条件。** 原话：「不设这个场景，无法预测什么时候再切换方案」。因此上表的备选触发只作为分析结论保留，**不作为预设的切换路径**；若前提 1 或前提 2 将来发生变化，应重新审议本 ADR 而不是自动切换。

## 最终决策

当前成立的前提：前提 1 ~ 前提 5。

因此选择 `方案 1`。模块只定两张表的**基本字段**，其余列一律由调用方声明：

- 向量表：`chunk_id` / `created_at` / `updated_at` / `embedding`
- 数据表：`chunk_id` / `path` / `start_line` / `end_line` / `created_at` / `updated_at` / `content`

扩展列怎么加，见 `simple_rag/repository/表结构约定.md`。

前提失效时的切换路径：**用户明确不预设**。前提 1（数据量）或前提 2（必返回 path）变化时，重新审议本 ADR。

## 决策原因

- 效率无显著差别的前提下，方案 1 能做到**更灵活的 SQL 组合**，并且**数据从 vec0 中解耦**（用户原话）
- 用户对方案 2 的排除论证：「在每次向量搜索都必须返回 path 的前提下，是必然进行 2 次搜索……方案 2 在这个前提下甚至不如方案 1，因为方案 1 和 2 都在这个前提下必然进行 2 次搜索，方案 1 还有一个好处是数据中心不依赖 vec0，实现解耦」
- 方案 3 被排除的核心：`file_path` 多值后，vec0 上做不了「按文件」的过滤（前提 4），而该能力要用就必须有普通表 —— 那就已经是分表了

## 后续影响

### 本次实现的范围：两个类各自独立、互不调用

- **vec0 本次不做任何改动**（用户原话：「vec0 当前不用做任何改变」）—— `Schema`、DDL 生成、`insert` / `search` / `get` / `update` / `delete` 全部保持原样。`Schema.fields` / `filterable` **保留**，它们就是调用方声明扩展列的通道
- `repository` 下**新增数据表，由独立的类持有**（与 `VecDB` 并列，不并入 `VecDB`）。两个类各自闭合 —— `ChunkStore` 的 `insert` / `delete` / `delete_by_path` / `get` / `ids_by_path` **只动数据表这一张表**
- **本次真正的变更在检索取数**（用户原话：「改变的是检索的时候当知道了 chunkid 了，其他字段数据从哪个表里读」）：按 `chunk_id` 取字段改从**数据表**读，vec0 退为纯向量检索
- **修订 [检索层以 vec 为中心](2026-09-29-检索层以vec为中心.md)**：正文来源从 vec0 改为数据表；RRF 融合与「search 返回 chunk_id + 融合分 + fields」的结论**不变**，但前提 1 / 3 / 4 需更新
- 数据表设计细节：一个 chunk 多 path 时分多行，所以 `chunk_id` 不能单独做主键；`path` 非空；`start_line` / `end_line` 必有值（由 `Segment.start_line` / `end_line` 直接落库）；建 `(chunk_id)` / `(path)` 两个索引

### 收口：跨两张表的联合操作（已实现，落在 `simple_rag.indexing`）

三件事都要求两张表协同，**2026-10-02 已实现**，落点是 `RagIndexingPipeline`（用户：「别改变 simple_rag\embedding 之外的内容」—— 该包 2026-10-02 更名为 `simple_rag.indexing`，见 1.6）：

| 联合操作 | 实现 |
|---|---|
| 同事务写两张表 | `store()`：一次入库产三条记录（vec0 + 数据表 + bm25），一个 `SAVEPOINT` 包住 |
| 按 `path` 的完整删除 | `delete_by_path()`：`ids_by_path` → 整个 chunk 作废（三张表一起） |
| 按 `path` 过滤的 KNN | `search_in_path()`：拼**子查询**形态的 KNN |

三者的共同结构是用户早先点明的：**两张表之间必然有一次「id ↔ path」的换算**（用户原话：「单纯的 chunkid 和 path 并不是有效的内容，只要是查找删除必然会进行 2 次操作（无论是当前知道 chunkid 需要知道他的地址，还是知道地址要拿到 chunkid 并操作 vec0）」）。所以它们**天然跨模块 —— 落在 `VecDB` 或 `ChunkStore` 任何一边都不对**。

**`VecDB` 一个字没改。** 1.4 里写的「给 `VecDB.search` 的 `where` 加列表（IN）支持」是**错的方向**，见下。

#### 更正：按 path 过滤必须用子查询，不能用参数列表

2026-10-02 复核探针 25 时发现，`chunk_id` 上的过滤在 vec0 里有**两种形态、两种时机**：

| 写法 | 时机 | k=5（候选 15）的实测 |
|---|---|---|
| `chunk_id in (select chunk_id from 数据表 where path = ?)` | **先筛后查** | 命中 ✅ |
| `chunk_id in (?, ?)`（参数列表） | **先取 k 条最近的、再筛** | **返回空** ❌ |

探针：库里 15 条，`id10` 与查询正交（最不像）、是唯一满足条件的行。k=5 时参数列表形态返回空，子查询形态返回 `id10`。原因是由**列的类型**决定的：`Schema.filterable` 里声明过的 metadata 列走预过滤，主键 `chunk_id` 只能当 KNN 取完之后的后置条件。

**推论**：参数列表形态想全召回就得让 `k ≥ 全库行数`（不是「k ≥ 候选数」——候选在全局距离序里的排位不可知），而 `k` 上限是 4096。所以它相对「取大 k 再在应用层筛」没有任何能力，只会**诱使人写小 k 然后静默少返回**。

三块的实测约束：

- **同事务**：两表同属一个连接，`insert` 用 `SAVEPOINT` 即可嵌套进外层事务（探针 12 已证普通表与 vec0 可同事务）
- **按 path 删**：数据表 `path` 索引 → `ids_by_path` → 删 vec0 → 清数据表行（探针 24 §5 实测完整链路 5.1 ms）
- **按 path 过滤**：见上表。过滤是「缩小范围提精度」而非加速手段，条件由调用方按场景给，模块不默认加

#### 跨表写 SQL 需要表名，所以两个包各公开了一个常量

`search_in_path` 要拼 `chunk_id in (select chunk_id from <数据表> where path = ?)`，而表名原先在 `_schema.py` 里。用户选择**公开**：`vec` 与 `chunk_store` 各自导出 `TABLE_NAME`，`vec` 另导出 `vector_to_sqlite_vector`（拼 KNN 时要自己绑查询向量）。
