# BM25 多实现统一接口（fts5 + rank_bm25）

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

BM25 一路原本只有 SQLite FTS5 一种实现，而 FTS5 的 `k1` / `b` 被**硬编码在
1.2 / 0.75**，SQL 层没有设置入口（[已知限制](../known-limitations/2026-09-29-fts5参数不可调.md)，
实测 FINDINGS.md §6.2）。要调参就需要第二种实现（rank_bm25 库的 `BM25Okapi`），
但两种实现的能力差异是本质性的：FTS5 可增量、数据在 db 文件里；`BM25Okapi`
构造即终态、纯内存、无任何修改方法。需要定：对外接口长什么样、能力差异怎么暴露、
分数语义怎么统一、rank_bm25 的数据放哪。

### 讨论范围

- `simple_rag/repository/bm25` 包的对外暴露面（接口、工厂、输出类型）
- 统一接口的方法集与语义（open / rebuild / insert / delete / replace / search）
- 两实现的分数方向约定、rank_bm25 的持久化方案
- 能力差异（增量 vs 全量、可调参 vs 不可调）在接口层的表达方式

### 非讨论范围

- 不给检索层 `RetrieverConfig` 加 k1/b 透传 —— 构造期定参，检索层没有消费者
- 不做 BM25Plus / BM25L / BM25Lucene 变体
- 不给 rank_bm25 做「写盘后全量重算」式的伪增量
- 不动 vec 包与 db 连接层

### 问题深度

架构级：这是「统一抽象怎么划」的问题 —— 抽象漏了能力差异会让调用方在运行期
踩坑，抽象多了会让接口充满对某个实现无意义的方法。同时第一次出现「同一概念、
两个持久化载体」的分叉（SQLite vs pickle 文件）。

## 现状（决策时点）

- FTS5 实现（原 `BM25Index`）直接暴露给 `retrieval` / `db` 层，无抽象层
- FTS5 的 `bm25()` 返回**负数、越小越相关**；检索层 RRF 融合**只用排名不用分值**
  （2026-09-29 检索层 ADR 已定）
- rank_bm25 0.2.2 源码核实：`BM25Okapi(corpus, k1, b)` 构造时可调参；不存语料、
  `get_scores` 按文档下标返回全量分数数组；无修改方法；空语料构造 0/0 除零；
  idf 有 epsilon floor（退化语料下可为负）
- 本项目 `Chunk.chunk_id` 是 blake2b hex（32 位）

## 决策前提

- 前提 1（事实，实测）：FTS5 的 k1/b 不可调 —— 本次重构的动机。
- 前提 2（事实，源码核实）：`BM25Okapi` 构造即终态，无增量方法 —— 用户在需求里
  明确表述「据我所知他不能实现增量更新和插入，只能重建，所以有些接口方法当使用
  这个时候要报错」。
- 前提 3（用户显式选择）：分数方向「**现在实现的是什么，就是什么**」—— 即保持
  FTS5 的负分约定。
- 前提 4（用户显式选择）：replace 语义 =「**覆盖或插入**」。
- 前提 5（用户显式选择）：rank_bm25 一路「**仅 BM25Okapi**」。
- 前提 6（用户显式选择）：持久化用 pickle，挂载方式选「**构造时给路径**」
  （open 自动加载、rebuild 自动写盘，接口不出现 save/load）。pickle 的想法由用户
  主动提出：「之前有一个ai和我说pickle可以持久化save和load啊」。
- 前提 7（用户对显式标注的默认项未提异议）：问题中明确写「这两个细节我直接定了，
  若有异议选 Other 说明」后，用户直接选了推荐项 —— ① pickle 存**纯数据**
  （chunk_id + 分好的 token），加载后重算 `BM25Okapi`，不 pickle 库对象；
  ② fts5 收到 k1/b/persist_path **显式报错**，不静默忽略。
- 前提 8（假设，未深究）：检索层没有跨实现逐位比较分数的需求 —— 依据是 RRF 只用
  排名（检索层 ADR）+ 用户对「分数方向保持现状」的选择。两实现的 idf 公式与
  默认参数不同，分数本来就不逐位可比。

## 可选方案与决策逻辑

### 决策点 1：对外暴露方式

| 方案 | 内容 | 结果 |
|---|---|---|
| A. ABC + 工厂 | `BM25Index`（抽象基类）+ `create_bm25(impl=...)`，具体类不出包 | **选定**（用户原始需求：「构造一个统一的向外接口类……不暴露fts5_bm25本体」） |
| B. 具体类直接暴露 | 调用方自己 import 选实现 | 否决 —— 换实现变成调用方改 import 路径 |

### 决策点 2：分数方向

| 方案 | 内容 | 结果 |
|---|---|---|
| A. 保持现状 | 负数、越小越相关；FTS5 原样，rank_bm25 取负 | **选定**（前提 3：「现在实现的是什么，就是什么」） |
| B. BM25 学术惯例 | 越大越相关；rank_bm25 原样，FTS5 取负 | 否决 —— 改动现状，且与 vec 的 distance 方向并存会造成两个方向 |

### 决策点 3：rank_bm25 持久化挂载

| 方案 | 内容 | 结果 |
|---|---|---|
| A. 构造时给 persist_path | open 幂等恢复、rebuild 自动写盘；接口无 save/load | **选定**（前提 6） |
| B. 显式 save/load 方法 | 接口多两个对 fts5 无意义的方法（数据本来在 SQLite） | 否决 |
| C. 纯内存不落盘 | 重启后调用方自己全量 rebuild | 否决（用户提出 pickle 后放弃）；但不给 persist_path 时仍保留此用法 |
| D. token 存 SQLite 普通表 | 与 fts5 同载体，但多一套表结构与加载校验 | 否决 —— 复杂度高于 pickle 且无独占收益 |

### 决策点 4：pickle 内容

| 方案 | 内容 | 结果 |
|---|---|---|
| A. 纯数据 + load 后重算 | pickle `(chunk_id, tokens)` 列表（带格式版本号），加载后重新构造 `BM25Okapi` | **选定**（前提 7①） |
| B. pickle 库对象 | 直接 pickle `BM25Okapi` 实例 + chunk_id 平行数组 | 否决 —— 绑定库内部属性布局（`doc_freqs`/`idf`/`doc_len`），库升级改属性名旧文件全部报废。用户最初的「save和load」设想即此方案，被此理由替换 |

### 决策点 5：能力差异的表达

| 方案 | 内容 | 结果 |
|---|---|---|
| A. 显式失败 | rank_bm25 的 insert/delete/replace 抛 `NotImplementedError`；工厂对错配参数（fts5 收 k1/b、rank_bm25 收 conn）抛 `ValueError` | **选定**（前提 2 + 前提 7②） |
| B. 静默忽略 / 伪增量 | 不支持的操作 no-op，或「写盘后全量重算」假装支持 insert | 否决 —— 配置没生效却不报，比报错糟糕；伪增量一次插入一次 O(N) 重算是性能陷阱 |

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |
| v1 | 「命中过滤」按 score > 0 实现 | 初版 rank_bm25.search 想对齐 FTS5「只返回命中」 | 测试实测暴露：`BM25Okapi` 在退化语料（词出现在过半文档，极端如单文档语料）下 idf 被 epsilon floor 成**负数**，命中文档得负分，被 score>0 误杀，search 返回空 |
| v2（最终） | 按**词命中**过滤（每篇文档的 token 集合判交集），分数只用于排序 | 退化语料下行为正确 | 连带修正契约表述：分数**符号**不能作契约（rank_bm25 取负后退化语料下可能为正），`BM25SearchResult` 的契约改为「**越小越相关（方向）**，符号不是契约」 |

## 最终决策

当前成立的前提：1~7 全部成立（8 为假设，暂无反例）。

选定：**统一接口 `BM25Index`（open / rebuild / insert / delete / replace / search）
+ `create_bm25` 工厂 + 双实现内聚子包**；分数保持「越小越相关」、rank_bm25 取负；
rank_bm25 持久化 = 构造时 `persist_path` + pickle 纯数据 + 原子写盘
（temp + `os.replace`）；能力差异显式报错，静默忽略被禁止。

前提失效时的切换路径：

- 前提 2 失效（rank_bm25 出现增量方案，或换支持增量的库）→ insert/delete/replace
  解禁，决策点 5 重议
- 前提 8 失效（出现跨实现比较分数的消费者）→ 决策点 2 重议，可能引入归一化层
- pickle 文件出现跨机器 / 长期归档需求（pickle 版本兼容性风险放大）→ 决策点 3
  切到方案 D（SQLite 普通表）

## 决策原因

- 工厂 + ABC 让「换实现」从改 import 路径降为改一个字符串参数 —— 这正是用户
  提出「不同的实现方法都要做成内聚的」的意图。
- pickle 纯数据比 pickle 对象多付一次 O(N) 内存重算（快），换来对库版本变化的
  免疫 —— 唯一的持久化格式绑定是我们自己的稳定形状。
- 显式报错让「调用方换实现」的能力差异在构造期 / 第一次调用时就暴露，
  而不是静默行为差异。
- 「越小越相关」与 vec 的 distance 同向，检索层 `RetrievalHit` 的「都越小越好」
  表述继续成立，改动面最小。

## 后续影响

- `retrieval` / `db` 层的 import 不变（`BM25Index` 名字保留给基类），只有构造处
  改走 `create_bm25`
- fts5 的 chunk_id hex 要求成为**实现差异**而非全局约束 —— 换实现时调用方要重新
  核对自己的 id 形状（README 有对照表）
- rank_bm25 的 pickle 文件**只应该加载自己写的**（pickle 反序列化可执行任意代码），
  带格式版本号拒载坏文件
- 待验证（README「未验证」节）：rank_bm25 在大语料下的内存占用与查询延迟
  （`get_scores` 全量打分）
