> **v1.1 修订（2026-10-01）** —— 触发者是 [向量数据分表](2026-10-01-向量数据分表.md)。

## 问题界定

### 问题简述

RetrievalClient 要综合两路检索：vec（向量）与 bm25（关键词）。直接暴露的问题是两路返回类型不同（`VecSearchResult` 带 fields，`BM25SearchResult` 只有 chunk_id + score）、分数单位不同（distance vs 负 bm25 分），没法合并排序。往下挖一层是立场问题：vec_db 与 bm25_index 是否对等依赖、search 的返回要不要带正文。用户点破：这个选择隐含着"vec 必须存在"这个未确认的前提，得先定立场再定接口。

### 讨论范围

- 检索层（simple_rag.retrieval）的依赖方式与返回形状
- 多路结果的融合方式（RRF，倒数排名融合）
- 融合后取不到内容时的行为

### 非讨论范围

- 存储层（repository/vec、repository/bm25）——本决策不改存储层任何代码
- 加权融合、分数归一化、rerank——砍掉（已与用户对齐），缺了它们 RRF 检索照常工作
- 各表之间的数据一致性——归写入方管，检索层只记录行为

### 问题深度

架构原则层：检索层与存储层的职责边界、模块依赖方向、接口契约的长期形状。

## 现状

**（下列 1~4 条是 v1.0 当时的情况；5 是 v1.1 修订后的状态。）**

- vec0 表设计自带任意业务字段（`Schema.fields`），正文存在这张表
- BM25 表按设计只存分词后的 token 串，无法取回原文；返回只有 chunk_id + score
- 项目里没有第二个存正文的地方
- 两路分数单位不可比：vec 的 distance 是 0~2 的距离，bm25 的分是无上界的负数
- bm25_store.py 的 docstring 明确写了：融合方式是检索层的排序决策，存储层不替它拍板
- **（v1.1，2026-10-01）** 正文与来源已搬到独立的数据表（`repository/chunk_store`），
  vec0 只负责向量检索

## 决策前提

- 前提 1：vec0 表带任意业务字段，正文存在这里（用户原话："当前的数据库设计上把大部分内容都放在了vec0表中"）
- 前提 2：BM25 表只存分词后的 token 串，取不回原文（存储层事实，bm25_store.py）
- 前提 3：项目里没有第二个存正文的地方（用户："除非一些数据单独作为一个表存在"——该表现在不存在）
- 前提 4（用户判断）：vec0 不存在则整个检索不存在——"如果vec0不存在，当前整个检索其实就不存在了"

**v1.1 修订（2026-10-01）**：**前提 1 与前提 3 已失效** —— 正文与来源搬到了数据表
（[向量数据分表](2026-10-01-向量数据分表.md)），项目里有了第二个存正文的地方。
前提 2 与前提 4 仍成立（BM25 仍取不回原文；没有向量表就没有向量检索）。

于是「vec_db 是内容仓库」不再成立 —— 这是本 ADR **唯一**被修订的地方。
「融合方式」与「返回形状」两个结论不受影响，见「最终决策」。

## 可选方案

### 方案 A：以 vec 为中心

vec_db 在 RetrievalClient 里承担两个角色：内容仓库（必然依赖，把 chunk_id 变回正文）；检索方式之一（配置 "vec" 才启用）。bm25 是"另一种产生 chunk_id 的方式"，分数只参与融合。search 返回 chunk_id + RRF 融合分 + fields。

**优势**

- 如实描述今天的数据模型：bm25 命中的 chunk 取正文只有 vec0 一个去处，依赖本来就存在，由检索层显式承认
- 调用方一次拿到正文，不必自己再查一遍

**劣势**

- 检索层对 vec 模块硬依赖
- bm25 命中但 vec0 缺行的 chunk 补正文时被静默丢弃，返回条数可能少于 k

### 方案 B：不以 vec 为中心（对称检索器）

所有检索方式对称返回薄结果（chunk_id + 分数），正文由上层自己取。

**优势**

- 接口完全对称，检索层不碰 fields
- 正文将来搬到独立内容表时，这层接口不用动

**劣势**

- 正文今天只能从 vec0 拿，调用方最终还是调 vec_db.get——前提没消失，只是挪给了调用方
- 真正收益要等独立内容表存在才兑现；按项目规则，不拿不存在的实现当设计依据

## 最终决策

**v1.1（2026-10-01）生效的结论：**

- **融合方式不变**：多路结果用 RRF —— 只看每路内部排名，第 i 名得 `1/(60+i+1)`，
  多路命中累加。分数只在各自来源内有效，**禁止跨来源比较**
- **返回形状不变**：`search` 返回 `chunk_id` + 融合分 + **正文与来源**
- **内容仓库换成 `ChunkStore`**（数据表）：`RetrievalClient` 必收它；融合完按
  `chunk_id` 取回 `content` 与 `sources`
- **`vec_db` 从必然依赖降为按需注入** —— 与 `embedding_client` / `bm25_index` 同级，
  只在启用了 vec 路时才要

检索流程：各路并发召回 → RRF 融合 → 截前 k 条 → 按 `chunk_id` 回数据表取内容。

前提失效的切换路径已**执行完毕**（v1.0 时就写明了这条路径：结构不动，只换取数来源）。

## 决策原因

- （v1.0 当时）正文只存在于 vec0，方案 B 的"对称"只是接口表面的对称，系统层面的依赖没有变
- （v1.0 当时）方案 A 把依赖显式化在检索层内部（构造函数必收 vec_db），比让每个调用方各自调 vec_db.get 更可控
- RRF 用排名绕开分数量纲问题，是"分数不可比"这个事实下的标准解；存储层 docstring 也把融合决策明确留给了检索层
- **（v1.1）备选触发果然由存储分层改动触发**：正文搬到数据表后，前提 1 / 3 同时失效。
  当初写下的切换路径是"结构不动、只换取数来源"——按它执行，检索层的结构确实没动

## 后续影响

- `RetrievalClient` 构造签名：`chunk_store`（数据表）必填；`vec_db` / `embedding_client` /
  `bm25_index` 都是可选关键字参数，依赖校验在 `_init_retriever` 按启用的检索器进行
- `RetrievalResult` 的形状：`chunk_id` / `score` / `content` / `sources` / `fields` ——
  **`sources` 是列表**，跨文件合并的 chunk 会有多条来源
- 已知行为：召回有但数据表缺行时静默丢弃，返回条数可能少于 k；一致性归写入方管，检索层不修数据
- 已砍（与用户对齐）：加权融合、分数归一化、rerank；RetrieverConfig 的 k1/b 死配置删除
- vec 检索器的 dimensions 必须可配：必须与建表 Schema.dim 一致，否则 search 直接报错
- 待验证：RRF K=60 在真实语料上的效果；若实测某一路总是噪声，再考虑加权（属调优，有实测证据再加）
