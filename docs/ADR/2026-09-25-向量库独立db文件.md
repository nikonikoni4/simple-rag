# 向量数据库使用独立 .db 文件

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档，记录从"同库"改为"独立文件"的决策 |

## 问题界定

### 问题简述

`simple_rag` 要建一个向量存储模块（将来抽象为独立 SDK 引入 LifePrism 桌面项目）。动手写 `repository` 之前必须先定一件事：**向量数据的物理存储位置** —— 与业务库 `lifewatch_ai.db` 同库，还是独立 `.db` 文件。

这个决策会连带决定连接管理、备份策略、迁移边界和同步边界，属于动手前必须锁死的架构前提。

### 讨论范围

- 向量数据的物理存储位置（同库 vs 独立文件）
- 由此衍生的连接管理、备份、迁移、同步四项边界
- 关键问题：独立文件带来的独立性收益，是否大于它引入的运维成本（两个文件的一致性）

### 非讨论范围

- 向量表的具体 schema（列设计、partition key 与 metadata 列的取舍）
- 连接管理方式（已另行确定为**单连接、不池化**）
- embedding 模型选型
- 是否同步向量数据（已确定为**不同步**，见「后续影响」）

### 模糊信息的明确定义

- `独立性`：本文中指**四层都要** —— (a) 可单独删除重建向量库而不触及业务数据；(b) 备份/分发粒度独立；(c) 代码层面 `repository` 不依赖业务库的连接与配置；(d) 生命周期独立。
- `迁移不方便`：本文中指**两个方向都受影响** —— 业务迁移（m001–m016 那套）碰到 vec0 表会出事；以及向量库自身的 schema 演进（vec0 不能 ALTER，只能整表重建）。

### 问题深度

涉及架构边界：存储分层、派生数据定位、SDK 抽取前提。不是浅层的方案选择。

## 现状

- RAG 项目正在 `explore/` 用一次性探针对 sqlite-vec 做可行性验证，为将来抽象 SDK 做准备。
- LifePrism 的业务库是 `~/AppData/.../dataset/lifewatch_ai.db`，含 17 个迁移脚本（m001–m016）。
- LifePrism 有文件 + 数据库双向同步（`sync/`）：数据库走 `SYNC_TABLES` 白名单 + hash_id + LWW；文件走 `SYNC_DIRECTORIES` 白名单 + diff3 三方合并。
- 探索阶段已实测确认的事实：
  - vec0 是虚拟表，在 `sqlite_master` 里占 **8 个条目**（本体 + 7 张影子表）。
  - vec0 表**不能** `CREATE INDEX`、**不能** `ALTER TABLE ADD/RENAME COLUMN`。
  - 影子表是**普通表**，能被**不带扩展的连接直接读写**（实测向 `vec_items_chunks` 写入成功，无任何报错）。
  - `PRAGMA table_list` **不**把 sqlite-vec 的影子表标记为 `shadow`，仍报 `table` —— 标准的"排除影子表"做法失效。
  - 删除行不回收 chunk 空间；**全量重建每轮泄漏约一个 chunk**（只有 `DROP TABLE` + `CREATE` 能规避）。
  - KNN + JOIN 的 `order by distance limit N` 写法失败；`k = ?` 或子查询/CTE 写法可用。

## 决策前提

- **前提 1（用户）**：**没有跨表 JOIN 查询的需求**。用户原话：「既没有join连表查询的需求」。
- **前提 2（用户）**：**需要四层独立性**。用户对「独立性具体指哪一层」的回答是「d 以上都要」。
- **前提 3（用户 + 实测）**：**迁移对 vec0 表不友好**，业务迁移与向量库自身 schema 演进**两个方向都受影响**。用户原话：「而且迁移也不方便」；对「指哪个迁移」的回答是「c 两个都是」。
- **前提 4（实测）**：**LifePrism 的迁移系统当前会枚举全表**。`m008_migrate_to_utc.py` 执行 `SELECT name, sql FROM sqlite_master WHERE type='table' AND sql IS NOT NULL`，会把 `vec_items` 与 7 张影子表全部取出；它靠 `if create_sql and _OLD_DEFAULT in create_sql` 做内容过滤跳过 vec0 表 —— **属于巧合而非设计**（protection 仅来自"vec0 的 CREATE SQL 里恰好不含 `datetime('now', 'localtime')`"）。
- **前提 5（实测）**：**迁移与同步用的连接不加载 sqlite-vec 扩展**。`migration_runner.py:37` 直接 `sqlite3.connect(db_path)`。对该连接而言 `SELECT ... FROM vec_items` 报 `no such module: vec0`，但 7 张影子表可读**可写**。
- **前提 6（实测）**：**`diary/*.md` 已在 LifePrism 文件同步白名单内**（`SYNC_DIRECTORIES` 含 `diary/`）。因此向量可从原文重建 —— 向量属于**派生数据**。

## 可选方案

### 方案 A：向量表放进业务库 `lifewatch_ai.db`

**优势**

- 单文件，备份/恢复只需处理一个文件，天然一致
- 将来若需要，可以做 KNN + JOIN 业务表

**劣势**

- 向量表与业务迁移系统共处一库，迁移中的全表枚举会撞上 vec0 表与 7 张影子表
- **无法单独删除重建向量库** —— 重建意味着动业务库
- vec0 不能 ALTER，向量 schema 演进只能整表重建，与业务迁移耦合
- 四层独立性一层都不满足

### 方案 B：向量数据独立 `.db` 文件

**优势**

- 迁移系统**完全隔离** —— 业务迁移不可能碰到 vec0 表
- **可单独删除重建**（删文件即可），不碰业务数据。这对 vec0 的 chunk 泄漏是**必需**的维护能力
- 备份/分发粒度独立
- 代码层 `repository` 不依赖业务库的连接与配置，SDK 抽取时边界干净
- 贴合"向量是派生数据"的定位：可从同步过来的 `diary/*.md` 本地重建

**劣势**

- 备份/恢复需处理两个文件，两者之间存在时间差，可能出现"业务数据新、向量旧"
- 无法做 KNN + JOIN 业务表（但前提 1 说明不需要）
- 多一条连接（已决定不池化，成本极低）

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1 成立（无 JOIN 需求） | 方案 A 失去唯一独占优势 | 「消掉对手方案理由」的论证 |
| 前提 2 + 3 + 4 + 5 成立（要独立性 / 迁移有真实干扰） | 方案 B | **当前选择** |
| 前提 6 成立（向量可从原文重建） | 方案 B 的备份不一致风险降级为可接受 | 索引过期 ≠ 数据丢失 |
| **前提 1 失效**（将来真需要跨库 JOIN 业务表） | 重新评估，可能回到方案 A 或引入第三方案 | 备选触发 |
| **前提 6 失效**（原文不再同步，或向量成为唯一原文存储） | 备份不一致升级为数据丢失风险，须引入跨文件原子备份 | 备选触发 |

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |
| v1 | 向量表放进业务库 `lifewatch_ai.db` | 单文件简单、备份天然一致 | 迁移系统会撞上 vec0 表；无法单独重建向量库；四层独立性都不满足 |
| v2 | 向量独立 `.db` 文件 | 迁移隔离 + 可单独重建 + 代码边界干净 + 贴合派生数据定位 | 备份需处理两文件一致性（由前提 6 降级为可接受）|

## 最终决策

当前成立的前提：**1、2、3、4、5、6 全部成立**。

因此选择 **方案 B：向量数据独立 `.db` 文件**。

前提失效时的切换路径：

- **前提 1 失效**（真需要跨库 JOIN 业务表）→ 重新评估，考虑合库或引入支持 JOIN 的向量层。
- **前提 6 失效**（原文不再同步 / 向量不可重建）→ 必须引入跨文件原子备份，否则备份不一致会从"索引过期"变成"数据丢失"。

## 决策原因

- **原因 1**：前提 1 消掉了方案 A 的唯一独占优势。vec0 的 metadata 列与辅助列本来就能在 KNN 查询里一次 SELECT 取出，不需要回表 JOIN；而 KNN + JOIN 的写法本身还受 `order by distance limit` 限制。既然不需要 JOIN，同库就只剩"单文件"这一个好处。
- **原因 2**：前提 3/4/5 说明同库存在**真实**的干扰风险，且**当前之所以没出问题，是靠 `m008` 的内容过滤巧合**。把向量移出去，这个隐患从"靠巧合成立"变成"结构上不存在"。
- **原因 3**：前提 2 的四层独立性，独立文件全部满足，同库一层都不满足。
- **原因 4**：前提 6 让独立库的主要代价（备份不一致）从"数据丢失"降级为"索引过期" —— 因为向量可从已同步的 `diary/*.md` 本地重建。

## 后续影响

- `_connection.py` 可保持**单库写法**（`simple_rag` 只连向量库，不连业务库）。
- 迁移模块（用户已定为**占位，暂不实现**）需要版本号机制；独立库让它的边界清晰 —— 只管向量库自己的 schema。
- **向量数据不同步**：`vec_items` **不进** `SYNC_TABLES`。各端从同步来的 `diary/*.md` 本地重建索引。
- **备份策略待设计**：两个文件分别备份存在时间差。因为向量可重建，风险可接受；但应在文档中写明，避免将来误判为 bug。
- LifePrism 集成时需新增：向量库路径配置、首次索引构建流程、重建索引的维护入口。
- **待验证事项**：
  - `SQLITE_DBCONFIG_DEFENSIVE` 能否保护 sqlite-vec 的影子表（因 `PRAGMA table_list` 未标记为 `shadow`，存疑）。
  - 独立库下两个文件的备份一致性方案。
