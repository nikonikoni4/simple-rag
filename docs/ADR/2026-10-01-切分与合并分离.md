# 切分与合并分离（_merge_small_chunks 提升为对外接口）

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

`_merge_small_chunks` 当前是 `cut` 的收尾步骤（由 `min_token` 参数触发），私有、且**只能在单文件内合并**。这挡住两件事：

1. **跨文件合并没有入口** —— 单文件过短时（整篇只切出一个 chunk），文件内没有邻居可并，该短块会被丢弃。日记场景大量存在这类文件。
2. **合并能力无法被复用** —— 外层调用方想自己控制合并时机与组合方式时，只能整体接受 `cut` 的行为。

触发这次决策的直接问题：做干扰块实验时确认小 chunk 在向量检索下是灾难级，紧接着发现单文件合并对「整篇只有一个短块」的文件只能丢弃 —— 那个缺口必须由跨文件合并补上，而跨文件合并需要一个可独立调用的合并原语。

### 讨论范围

- `chunking/structured_file` 的对外接口形状：`cut` / `chunk_by_title` / `chunk_md_files` 与合并函数的关系
- `min_token` 参数的归属与去留
- 「要不要合并」这个决策落在哪一层

### 非讨论范围

- 合并算法本身（`_merge_small_chunks` 的归宿规则不改：并进上一个 → 并进下一个 → 两者都没有则丢弃）
- `chunk_md_files` 的具体实现（本次只定它与合并接口的关系）
- 面包屑 / 文件名前缀（另行决策）

### 模糊信息的明确定义

- `小 chunk`：token 量低于阈值的 chunk（阈值由调用方传）
- `不足一个 chunk 的文件`：切分后只产出 0~1 个 chunk 的文件（例如只有一两句话的日记）

### 问题深度

模块接口设计层：切分与合并的职责边界，决定 `chunking` 模块的对外契约形状，以及调用方如何组合这两步。

## 现状

- `_merge_small_chunks` 是私有函数，只在 `cut` 内部被调用
- `chunk_by_title` / `cut` 带 `min_token` 参数，传了就自动做**文件内**合并
- 合并的归宿规则：并进上一个 → 并进下一个 → 两者都没有就丢弃（整篇只有一个短块时**丢弃**）
- `chunk_md_files` 目前只有 docstring，未实现
- 实测语料里存在 13 token 级别的短块（`_merge_small_chunks` docstring 记录了该块在多个不相关查询里排第 1）

## 决策前提

- **前提 1：小 chunk 的检索危害已实测。**
  - 向量侧是灾难级：52 个沾边小 chunk 把 vec 单路 MRR 从 0.804 打到 **0.372**，Hit@1 从 65.4% 掉到 **15.4%**，26 条 query 的干扰块全部进前 10、平均第 1.7 名（`explore/实际测试/e2e检索测试/干扰块实验.md`）
  - BM25 侧同样这批只掉 0.019，但注入远短于平均的 chunk 会把 fts5 的 **avgdl 从 724.5 拉低到 609**，长文档的长度惩罚变重，也受到一定影响
- **前提 2：当前语料中会出现「不足一个 chunk 的文件」** —— 用户确认其日记中确实存在很短的日记。这类文件在单文件合并下没有邻居可依附，会被丢弃
- **前提 3：合并有独立使用的实际需求**，两个来源：`chunk_md_files`（跨文件合并，处理单文件过小）与外层调用方自行组合

## 可选方案

### 方案 A：合并外置为公开接口

`cut` / `chunk_by_title` 只负责切分；`merge_small_chunks(chunks, min_token)` 作为公开接口；`chunk_md_files` 内部调用它（逐文件切 → 汇总 → 跨文件合并）。

**优势**

- 单一职责：切分与合并是两个正交决策，各自可独立测试
- 可复用：跨文件合并与外层自定义组合共用同一个原语
- 「要不要合并」成为调用方的显式决策 —— 与实测结论一致（危害大小取决于召回路线：单路向量灾难、BM25 轻微、融合能吸收大半）

**劣势**

- 调用方忘记合并时，小 chunk 直接进库（单路向量检索下是灾难）—— 靠文档警告，不靠默认值兜底
- 调用链多一步

### 方案 B：保持现状（cut 内部合并）

**优势**

- 调用方不会忘；接口简单

**劣势**

- 无法跨文件合并，单文件过短的文件只能丢弃
- 合并策略藏在切分器里，调用方无法单独调整或关闭

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1 + 前提 2 + 前提 3 成立 | 方案 A | 当前选择 |
| 若前提 1 的危害被消除（检索链路固定包含 BM25 且不跑单路向量）**且** 前提 2 仍成立（跨文件合并仍需要） | 方案 A 仍成立（合并原语仍被 chunk_md_files 需要） | — |
| 前提 2 与前提 3 同时失效（不再有短文件、也不需要跨文件合并） | 方案 B 可重新评估 | 备选触发 |

## 最终决策

当前成立的前提：前提 1、前提 2、前提 3。

因此选择 `方案 A`。

连带决定（用户明确选择）：**`min_token` 参数从 `cut` / `chunk_by_title` 删除** —— 它失去唯一用途，合并统一走 `merge_small_chunks`。

## 决策原因

- 单一职责原则。用户原话：「一个函数只完成一件事情这个原则上来说符合这个原则，而且容易测试」
- 实际需求。用户原话：「当前有实际需求需要单独使用这个合并（一方面是对内 chunk_md_files，用于处理单文件过小导致 chunk 过小无法合并的问题；另一方面是外层也可以自己调用这个合并，有一定灵活性）」
- 与实测一致：合并的必要性取决于召回路线，是调用方按自己的检索链路决定的事，不该由切分器替它拍板

## 后续影响

- `cut` / `chunk_by_title` 接口收窄（删 `min_token`）
- 新增公开接口 `merge_small_chunks`
- `chunk_md_files` 实现时复用该接口（逐文件切 → 汇总 → 合并）
- 调用方文档需显眼标注前提 1 的实测数据（小 chunk 在单路向量检索下的危害）
- 单测：合并的归宿规则可独立测试，不再需要构造完整文件来触发
- 相关：跨文件合并会让 `file_path` 变多值，承载方式见 [向量数据分表](2026-10-01-向量数据分表.md)
