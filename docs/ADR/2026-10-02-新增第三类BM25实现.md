# 新增第三类 BM25 实现（走数据库，数据表自设计）

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

现有两类 BM25 实现各有一处不满足需求：`fts5` **不能修改参数**，`rank_bm25`
**每次需要把全部内容读进内存**。需要一个走数据库、数据表由本项目自己设计的
第三类实现。本次只把这个决策记下来，不落实现。

### 讨论范围

- 是否新增第三类实现
- 它的大方向：走数据库、数据表由本项目自己设计
- 它对既有两类实现的影响

### 非讨论范围

- **实现细节** —— 用户原话「不包含实现细节」。表结构、列怎么设计、打分公式怎么落，
  都不在本次
- **命名** —— 用户原话「不需要写命名」。工厂参数名与子包名另行决定
- **抽象接口本身** —— 用户原话「当前的抽象接口已经设计好了的」
- **`fts5` 与 `rank_bm25` 两个既有实现** —— 本次不动

### 模糊信息的明确定义

- `走数据库`：数据落在注入了连接的 SQLite 里，不常驻 Python 进程内存，而不是
  指必须与 `vec` 共用同一个 `.db` 文件
- `数据表是自己设计的`：表结构由本项目定，不套用 FTS5 的虚拟表形态

### 问题深度

存储层选型的补充决策。前一次（[BM25 多实现统一接口](2026-09-29-BM25多实现统一接口.md)）
定的是「统一接口 + 双实现」；本次是在既定的统一接口下再补一个实现，理由是前两个
各差一块。它决定后续若干次实现的边界，因此需要留档。

## 现状

- 统一接口 `BM25Index`（`open` / `rebuild` / `insert` / `delete` / `replace` / `search`）
  已定，调用方经 `create_bm25(impl=...)` 拿到实例，具体实现类不出包
- 两个既有实现：`fts5`（走调用方注入的 SQLite 连接）、`rank_bm25`（纯内存 + 可选 pickle）
- FTS5 的已知限制：`bm25()` 不接受 `k1` / `b`，额外参数是**列权重** ——
  见 `docs/known-limitations/2026-09-29-fts5参数不可调.md`
- 2026-10-02 实测：`rank_bm25` 的常驻内存随语料**严格线性**，50,000 篇 **1,927 MB**
  （≈38 KB/篇）；同样数据放 SQLite 只有 ~2 MB 页缓存。探针与完整数据见
  `explore/bm25/README.md`

## 决策前提

- **前提 1（用户明确表述）**：FTS5 不能修改参数。
  原话：「原因是：1. fts5不能修改参数」。
  有既有实测支持 —— FTS5 的 `k1` / `b` 硬编码在 1.2 / 0.75，`bm25(t, 1.2, 0.75)`
  里的参数是列权重，不是 `k1` / `b`。
- **前提 2（用户明确表述，本次实测确认）**：`rank_bm25` 每次需要把全部内容读进内存。
  原话：「2. rank_bm25每次需要把全部内容都读进内存」。
  2026-10-02 实测确认：50,000 篇常驻 1,927 MB，≈38 KB/篇，四个量级上线性。
  来源是 `BM25Okapi` 为每篇建的 `{词: 频次}` 结构加全库 token 串；
  **与 pickle 无关** —— pickle 文件只有 45.2 MB，是常驻内存的 1/40。
- **前提 3（用户明确表述）**：新实现走数据库，数据表由本项目自己设计。
  原话：「这个bm25还是走的数据库，但是数据表是自己设计的」。
- **前提 4（用户明确表述）**：抽象接口已设计好，本次不改动。
  原话：「当前的抽象接口已经设计好了的」。
- **前提 5（用户明确表述）**：本次不写实现细节。
  原话：「不包含实现细节，就只说明下面需要自己实现数据库的bm25」。

## 可选方案

### 方案 1：新增第三类实现（走数据库 + 自设计数据表）

**优势**

- 同时避开前提 1 与前提 2：打分参数由本项目掌握，内存不随语料线性增长
- 数据表自己设计，表结构不套用 FTS5 的虚拟表形态

**劣势**

- 多一个实现要维护，`repository/bm25` 从两个实现变成三个
- 打分公式与全库统计量（`IDF` / `avgdl`）要自己落 —— 这部分工作量未知

### 方案 2：维持现有两类，不加

`fts5` 只用于不调参的场景，需要调参时用 `rank_bm25`。

**优势**

- 零新增代码，现有 153 个用例覆盖的两个实现不动

**劣势**

- 前提 1 与前提 2 仍在 —— 需要调参且语料大时，两条同时踩中，无解
- `rank_bm25` 没有增量（`insert` / `delete` / `replace` 抛 `NotImplementedError`），
  改数据只能全量 `rebuild`

### 方案 3：等 FTS5 上游开放 `k1` / `b`

**优势**

- 不新增实现

**劣势**

- 不受本项目控制，没有时间表
- 不解决前提 2（`rank_bm25` 的内存与 FTS5 无关）

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1（fts5 参数不可调）+ 前提 2（rank_bm25 全量内存）同时成立 | 方案 1 | 当前选择 |
| 前提 1 失效（FTS5 开放 `k1` / `b`） | 方案 1 的「可调参」这一半动机消失 | 重新审议 |
| 前提 2 失效（`rank_bm25` 出现内存有界的方案） | 方案 1 的「内存」这一半动机消失 | 重新审议 |

上表的备选触发是**分析结论**，本次未与用户确认切换路径。前提 1 或前提 2 变化时，
应重新审议本 ADR，而不是自动切换方案。

## 最终决策

当前成立的前提：1 ~ 5。

因此选择 `方案 1` —— 新增第三类 BM25 实现，走数据库，数据表由本项目自己设计。

本次**只记录决策，不落实现**（前提 5）：不在 `simple_rag/` 里加任何代码，
工厂里也不加这个名字。

## 决策原因

- 前提 1 指出 `fts5` 唯一的缺口是参数；前提 2 指出 `rank_bm25` 唯一的缺口是内存。
  两者各自缺的恰好是对方有的 —— 而这两条同时需要时，现有两类都顶不上。
- 前提 3 让新实现的表结构由本项目定，打分公式与统计量的落法不再受 FTS5 的
  硬编码或 `BM25Okapi` 的内存布局约束。
- 相比方案 3，方案 1 可控；相比方案 2，方案 1 才真正解掉前提 1 与前提 2。

## 后续影响

- `repository/bm25` 的对外三样（`BM25Index` / `BM25SearchResult` / `create_bm25`）
  不变（前提 4）
- `fts5` 与 `rank_bm25` 两个既有实现本次一个字不改
- **待下一次决策**：新实现的命名、表结构、列设计、打分公式的落法 ——
  本次明确排除（前提 5）
- **待验证**：新实现在本项目语料规模下的实际收益。内存收益在语料大到一定程度才显著 ——
  1,000 篇时 `rank_bm25` 只占 38 MB，量级上不构成问题
- 本次实测的口径：SQLite 侧的 1~2 MB 是**进程私有常驻**，不含 OS 文件缓存。
  87 MB 的 `.db` 仍会被 OS 缓存住，但那是可回收的
