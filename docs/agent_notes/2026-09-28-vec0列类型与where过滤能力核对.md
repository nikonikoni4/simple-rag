## 版本

| 版本 | 更新内容 |

## 1. 起因

在阅读 [simple_rag/repository/vec/_schema.py](../../simple_rag/repository/vec/_schema.py) 的 `Schema.filterable` 字段时，
追溯出两条与先前认知不一致的结论：

1. 先前得到的说法是「能在 KNN 的 where 里过滤的，只能取等号」。
2. 先前得到的说法是 sqlite-vec 只有 3 种列（附加列 / metadata 列 / 向量列）。

本次核对后发现：

- 第 1 条在**库层面不成立**（metadata 列支持等值之外的范围、IN、OR 等），在**模块层面成立**。
- 第 2 条**不完整**：库层面至少有 5 类列。

本报告固定事实、判定偏差性质，并给出结论。**所有结论均指向 explore 探针的实测记录，不做推断。**

## 2. 事实核对：库层面（sqlite-vec）到底有什么

### 2.1 列类型：5 类，另加隐藏列

出处：[explore/sqlite-vec/FINDINGS.md §4](../../explore/sqlite-vec/FINDINGS.md)、[§7 主键](../../explore/sqlite-vec/FINDINGS.md)、[§11.6](../../explore/sqlite-vec/FINDINGS.md)、探针 03 / 06 / 18。

| 角色 | DDL 写法 | 数量上限 | 能否 SELECT | KNN 里 WHERE | 能否 UPDATE |
|---|---|---|---|---|---|
| 向量列 | `embedding float[N] [distance_metric=…]` | 必需 1 个 | ✅（原始 blob） | 用 `match`，非过滤 | — |
| 主键列 | `chunk_id text primary key` | 0/1 个 | ✅ | ✅ 等值 | ❌（库拦） |
| metadata 列（普通列） | `name text`（无前缀） | 16 | ✅ | ✅ 等值 / 范围 / IN / OR | ✅ |
| partition key（分区键） | `name text partition key` | — | ✅ | ✅ 仅等值 / 范围，IN / OR **崩** | ❌ |
| 辅助列（加号列） | `+name text` | 16（与 metadata **独立**） | ✅ | ❌ **禁止** | ✅ |
| 隐藏列 | `distance` / `k` | — | `distance` 可读 | `k` 用于 KNN | — |

要点：

- 主键**不占** metadata 的 16 名额（§11.6 实测）。
- 隐藏列要用 `pragma table_xinfo` 才看得全（`pragma table_info` 的类型列是空字符串）。
- partition key 是 metadata 列的**变体**，能力是其子集，不是独立第四类。

> 换句话说，先前说的「3 种」（附加列 / metadata 列 / 向量列）漏掉了 **主键列**、**partition key** 与**隐藏列**。

### 2.2 where 过滤：metadata 列不止等号

出处：[FINDINGS.md §4 表格](../../explore/sqlite-vec/FINDINGS.md)、探针 03 第 8 段、探针 06 第 2/3/4/5 段。

metadata 列（即本模块的 `filterable` 对应的列）在 KNN 的 `where` 里，实测支持：

| 形态 | 例子 | 结果 |
|---|---|---|
| 等值 | `source = 'diary'` | ✅ |
| 范围 | `source >= 'x'` | ✅ |
| `IN` | `source IN ('a','b')` | ✅ |
| `OR` | `source = 'a' OR source = 'b'` | ✅ |
| `!=` | `source != 'diary'` | ✅ |
| 多条件 | `doc_date = … AND source = …` | ✅ |

只有 partition key 受限（IN / OR 会崩），但本模块没有使用 partition key。

> 所以「能在 KNN 里 where 的只能取等号」在库层面是错误的。

## 3. 事实核对：本模块 / spec 实际是怎么写的

核对对象：[设计 spec §3、§4.4、§7.1、§10](../superpowers/specs/2026-09-25-vec-db-repository-design.md) 与源码
[simple_rag/repository/vec/_store.py](../../simple_rag/repository/vec/_store.py)、[_schema.py](../../simple_rag/repository/vec/_schema.py)。

### 3.1 模块用了哪几类列

见 [_schema.py 的 build_ddl](../../simple_rag/repository/vec/_schema.py)：

- 向量列：`embedding float[dim] distance_metric=…`
- 主键列：`chunk_id text primary key`
- metadata 列：`created_at` / `updated_at` + **`Schema.filterable` 里的字段**
- 辅助列：**不在 `filterable` 里的字段** → `+name text`

即：**库有 5 类，模块只用了其中 4 类**（没有用 partition key）。

### 3.2 等值限制是「模块契约」，不是「库限制」

见 [_store.py 的 check_where / build_search](../../simple_rag/repository/vec/_store.py)：

- `check_where` 的 docstring 明写「只支持**等值**过滤，且只在 `search` 里生效」。
- `build_search` 拼死的形态就是 `[key] = ?`。

同一结论在 spec 里**也是按「模块的取舍」写的**：

- [§4.4](../../docs/superpowers/specs/2026-09-25-vec-db-repository-design.md)：「只作用于 `search`，**只支持等值**」——写在对外 API 章节。
- [§10「不做」表](../../docs/superpowers/specs/2026-09-25-vec-db-repository-design.md)：
  `范围 / IN / OR 过滤` 的理由是「只支持等值也能工作；当前无需求」；
  `partition key` 的理由是「它是性能优化，按 CLAUDE.md 属下游决定」。
- [§7.1](../../docs/superpowers/specs/2026-09-25-vec-db-repository-design.md) 里也明确写了「不支持 partition key」。

**所以：spec 文本本身没有把「只能等号」说成库的硬限制；它把范围 / IN / OR 与 partition key 列为「主动砍掉」。**

## 4. 判定

### 4.1 「只能在 KNN 里取等号」

- **在库层面：错**——metadata 列支持等值、范围、IN、OR、!=（§2.2）。
- **在模块层面：对**——本模块只实现等值（§3.2）。

### 4.2 「只有 3 种列类型」

- **在库层面：不完整**——至少 5 类（§2.1）。
- **在模块层面：接近对**——模块确实只用了 3~4 类（§3.1）。

### 4.3 必须分两个轴看（结论已修正）

**轴一：技术实现的最小化 —— 符合准则。**
按 [CLAUDE.md](../../CLAUDE.md) 的判定标准「缺了它，模块还能不能工作」：

- **只支持等值**：范围 / IN / OR 缺了，模块仍能工作 → 属「不做」。
- **不用 partition key**：partition key 缺了，模块仍能工作 → 属「不做」。
- 两者在 spec §10 都被**显式列为主动砍掉**。代码实现本身自洽。

**轴二：决策过程 —— 严重违规。**
但「缺了还能工作」只回答「模块能否运行」，**不回答「用户要的功能是否还在」**。
范围过滤对模块是可选枝节，对用户是**目标功能**。agent 在**未告知用户**的情况下砍掉它，
这一取舍在**流程层面是严重错误**，不能以「符合勿增实体」为它背书。
详见 [2026-09-28-砍功能前必须与用户对齐](2026-09-28-砍功能前必须与用户对齐.md)。

> ⚠️ 本文档初版只看了轴一，据此写过「设计没有问题」——**该结论已修正**：
> 技术实现自洽，但决策过程错误。二者不可混为一谈。

### 4.4 叠加在流程错误之上的「表述失真」

即便砍掉本身成立了，agent 还把「模块主动砍掉的能力」表述成了「库做不到的能力」：

- 这会让使用者对 sqlite-vec 的真实能力形成**不完整模型**（以为库只能等值、只有 3 类列）。
- 危害在于：将来若真需要范围过滤（例如按时间筛），会误以为「库不支持、得换方案」，而实际只是**模块没开放**，改 `_store` 即可。
- 按 [user-design-summary.md 的观察](../ADR/user-design-summary.md)，用户的理由陈述天然是压缩的、可能不精确——本条偏差符合该模式，宜以本文档固定准确表述。

## 5. 影响与建议

| 项 | 说明 |
|---|---|
| 对现有代码（技术层） | 等值限制与列类型用法实现自洽，无 bug |
| 对现有设计（流程层） | ⚠️ 砍掉范围 / IN / OR **未告知用户**，是流程错误 → 详见 [砍功能前必须与用户对齐](2026-09-28-砍功能前必须与用户对齐.md) |
| 对认知 | 记住两条：库的 metadata 列支持等值 / 范围 / `IN` / `OR`；库有 5 类列。本模块现开放等值与范围、只用 3~4 类列 |
| **已决定（2026-09-28）** | 开放**范围比较**（`>` / `>=` / `<` / `<=`）；`IN` / `OR` 仍不做。见 [砍功能前必须与用户对齐](2026-09-28-砍功能前必须与用户对齐.md) |
