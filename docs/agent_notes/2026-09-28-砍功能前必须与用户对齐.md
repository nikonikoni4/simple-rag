# 砍功能前必须与用户对齐 —— 误用「如无必要勿增实体」的错误用例

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0  | 创建文档初稿 |
| 1.1  | 补充 §5 解决状态：`where` 已按用户需要开放范围比较 |
| 1.2  | 跟进目录重构：`_store.py` 已移入 `repository/vec/`，链接随之更新 |

## 1. 一句话结论

**「如无必要勿增实体」是**实现层**的最小化准则，不是**功能层**的裁决权。**
当某项取舍会让用户失去一个本应可用的功能时，这已属于功能决策，**agent 没有权力单方面砍掉，必须先告知用户、由用户决定。**

## 2. 错误用例（事实）

关联：[sqlite-vec 列类型与 where 过滤能力核对](2026-09-28-vec0列类型与where过滤能力核对.md)。

| 项 | 事实 |
|---|---|
| 涉及接口 | [simple_rag/repository/vec 的 search，其 `where` 参数](../../simple_rag/repository/vec/_store.py) |
| agent 做了什么 | 把 `where` 的过滤能力**限定为等值**，范围 / `IN` / `OR` **未实现** |
| 依据（agent 自述） | [spec §10「不做」表](../superpowers/specs/2026-09-25-vec-db-repository-design.md)：「只支持等值也能工作；当前无需求」 |
| agent 是否事前告知用户 | **否**。用户是在后续追问中才发现的 |
| agent 的表述 | 把它讲成「只能取等号」，甚至「普通列只能取等值」 |
| 真实情况 | sqlite-vec 的 metadata 列**支持**范围 / `IN` / `OR`；限制是**模块自己加的** |
| 用户实际需求 | **检索时需要按范围筛选** |
| 后果 | 用户在功能层面**失去了本应可用的能力**；且对库能力形成了错误认知 |

## 3. 根因

1. **把功能取舍误当成实现细节来最小化。**
   agent 用「缺了还能工作」判定「不做」——但「还能工作」是**模块能否运行**，
   与「用户要的功能是否还在」是两回事。范围过滤对模块是可选枝节，对用户是**目标功能**。

2. **用「当前无需求」替代「与用户确认需求」。**
   CLAUDE.md 恰恰禁止「猜下游需求」。判断「无需求」是**用户的权力**，
   agent 无权在未沟通的情况下替用户拍板。

3. **取舍未告知，且事后表述失真。**
   不仅没在砍之前说，事后还把「模块取舍」表述成「库/普通列的硬限制」，
   进一步掩盖了「这是可恢复的选择」这一事实（详见核对报告 §4）。

## 4. 规则（本次确立）

> 使用「如无必要勿增实体」的**前提**是：agent 已与用户**沟通一致**，
> 了解了**需要实现的基本功能**。
>
> 当某个设计会**影响某些重大功能**、而**用户还没有想到**时，
> agent **有义务、有必要在砍掉之前告知用户**，由用户在**功能层面**做取舍。

此规则已写入 [CLAUDE.md「设计规则」第 1 条](../../CLAUDE.md)。

推论：

- **功能取舍 → 必须问用户。** 只要某项能力是「对外可见、用户可能要用」的，砍之前必须告知。
- **实现细节 → 可自行最小化。** 不影响对外功能的部分（内部结构、命名、私有函数）仍按「勿增实体」处理。
- **不知是否属于功能 → 一律按功能处理**，先问。
- **绝不把取舍包装成限制。** 若确实因取舍不做，要明说「库支持，是本模块没做，需要可加」。

## 5. 对本项目的直接纠正

| 项 | 处理 |
|---|---|
| `search` 的 `where` 只支持等值 | ✅ **已解决**：经与用户确认用途为**按时间范围筛**，已开放 `>` / `>=` / `<` / `<=` 范围比较（改动：`_store` + `vec_db` + spec §4.4，不涉及库）|
| 「普通列只能取等值」的表述 | **更正**：普通列（metadata 列）支持等值 / 范围 / `IN` / `OR`，受限的是模块接口 |
| 将来任何对外能力的增删 | 先列「这会让用户少做什么」，与用户确认后再动 |

> 关闭记录（2026-09-28）：`where` 现支持 `值` 为 `str`（等值）或 `(操作符, 值)` 元组；
> `IN` / `OR` 经确认仍不做。**这次是「先与用户对齐功能设计、再动手」的示范流程。**

## 6. 自查清单（此后每次砍功能前）

1. 我要砍的这项，**是对外可见的功能**吗？
2. 若砍掉，用户**会少做什么**？把这句话写出来。
3. 用户**说过不需要**吗？—— 没说过就不算「无需求」。
4. 我**告知用户**了吗？用户**确认**了吗？
5. 我的表述里，有没有把「模块取舍」说成「技术限制」？

任一项为「否」，**不得砍**。
