# 表结构约定 —— 基本字段 + 外部声明的列

本层有**两张表**：向量表（vec0）与数据表。两张表用的是**同一套字段模型**：

> **模块定「基本字段」，其余列由调用方声明。**

## 一、基本字段（写入时必须给）

基本字段是模块自己工作要用的那一批，DDL 由模块固定生成，调用方写入时必须提供。

| 表 | 基本字段 |
|---|---|
| 向量表（vec0） | `chunk_id` / `created_at` / `updated_at` / `embedding` |
| 数据表 | `chunk_id` / `path` / `start_line` / `end_line` / `created_at` / `updated_at` / `content` |

- `created_at` / `updated_at` 由模块维护，调用方不传。
- 数据表的 `path` / `start_line` / `end_line` 是**一行一组**：一个 chunk 有多个 path 时**分行存放**，每行带上该 path 自己的行区间。

## 二、其余列由外面给

两张表都允许调用方声明自己的列，机制是同一个 —— **构造时给出列名**。

vec0 现在就是这么做的（`Schema.fields`，见 [vec/README.md](vec/README.md)）；数据表同理。

模块不认识这些列代表什么，也不预判将来需要哪些列。加什么、存什么、要不要索引，都是调用方的决定。

### vec0 的唯一特殊之处：要区分 metadata 与辅助列

vec0 的两类列**能力不同**：

| 列类型 | 能 SELECT | 能进 KNN 的 `where` |
|---|---|---|
| metadata（普通列） | ✅ | ✅ |
| 辅助列（加号列） | ✅ | ❌ |

所以 vec0 声明扩展字段时要**额外说明**哪些是 metadata（`Schema.filterable`），哪些是辅助列。

**数据表是普通 SQLite 表，没有这个区分** —— 它的列一律能进 SQL 的 `where`。

## 三、vec0 本次不做改动

本次变更**不触碰 vec0**：它的 `Schema`、DDL 生成、`insert` / `search` / `get` / `update` / `delete` 全部保持原样。

## 四、变的是检索取数：知道 `chunk_id` 之后从哪张表读

检索的**流程不变**：各路召回产出 `chunk_id` → RRF 融合 → 按 `chunk_id` 取回其余字段。

变的只是**最后一步的数据源**：

| | 之前 | 现在 |
|---|---|---|
| 按 `chunk_id` 取正文、path、行区间等字段 | 从 **vec0** 读 | 从**数据表**读 |

分工随之明确：

- **向量表（vec0）** —— 只负责向量检索（KNN）。它不再是内容仓库。
- **数据表** —— 按 `chunk_id` 取回字段。**一个 chunk 可能对应多行**（多 path），读取时要按 `chunk_id` 取全部行。

## 五、数据表的持有方式

数据表由**独立的类**持有，与 `VecDB` 并列，不并入 `VecDB`。

两张表同属一个连接，所以「同事务写两张表」用 `SAVEPOINT` 即可成立 ——
写法与本包 README 的「[几张表怎么保持一致](README.md#几张表怎么保持一致)」一节相同。
